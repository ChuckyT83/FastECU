# J2534 Adapter Manager

Open **Tools → J2534 Adapter Manager**, select an available adapter and click
**Test Connection**. Refresh reads registrations and the packaged driver manifest.
The previous valid selection is preferred. Unsupported entries remain visible;
the status/tooltip explains why. No driver installation or registration is changed.

The test performs adapter Open, ReadVersion and Close only. It never creates a
CAN channel, sends vehicle requests, identifies an ECU or changes firmware.
It works independently of vehicle/DLC connection. No approval dialog, user hash,
manual worker invocation or report export is required. Returned versions and
actual errors appear in the dialog; expand Technical details for statuses,
driver error text and OpenPort lifecycle evidence. Stop other adapter applications
before testing. A failed test is never retried automatically.

The application runs its packaged diagnostic component asynchronously. Native
adapter calls remain in the existing detached worker. The parent waits 15 seconds,
never kills an adapter call and automatically observes late results without
repeating adapter calls. Pending/uncertain tests disable overlapping tests, even
when the dialog is closed and reopened. Closing the application does not authorize
retry/recovery of a still-running worker. Windows ownership mutexes also exclude
concurrent manager workers in the session. A currently open FastECU transport
prevents starting a test.

Adapter selection/descriptors are shared in `serial_port/j2534_adapter_selection.h`.
The choice is saved as `J2534/selectedAdapter` in Qt application settings. Future
operations can consume that selection; this milestone deliberately does not
redirect existing Subaru identification/flashing transports or enable programming.

OpenPort uses `adapters/openport/adapter-manifest.json`, the reviewed source/build
manifest and SHA-256 pins generated by the build pipeline. The application and
worker are built for that exact driver/dependency pair. Registered installed
copies with the same reviewed hash and colocated dependency are supported too.
Future reviewed builds update the manifest and compile-time pin automatically;
the user never enters hashes. Editing a manifest cannot admit arbitrary DLLs.
Proprietary or earlier OpenPort DLLs remain unavailable; no updater is bundled.
USBQUAL/1 acknowledges initialization/shutdown separately from USB resource release.
Void cleanup calls cannot independently prove Windows kernel-handle release.

OBDX discovery requires an OBDX VX registry model plus embedded OBDX product and
OBDX/Envyous company information, a compatible PE architecture, API 04.04 and an
accessible hashable DLL. A registry/display name alone is insufficient. This is
vendor metadata recognition, not cryptographic authentication or proof of physical
model. Install the official vendor package; unsupported/missing metadata is shown
explicitly. No proprietary OBDX DLL is redistributed. OBDX uses standard J2534
results, not custom OpenPort markers. GetLastError is used only after failures.

The Windows development package contains the GUI, internal diagnostics and
maintained OpenPort driver with libusb/license/source notices. Extract it together;
there is no System32 copying, driver rebinding or toolkit assembly step.
Tests use synthetic mock DLLs, never real hardware. Native CI and physical results
must be reported separately; a mock pass does not qualify an adapter or ECU.
